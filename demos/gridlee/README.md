# Gridlee: three bytes say three

![Gridlee in play, the grid running to the horizon](screen.png)

Videa's *Gridlee* (1983) runs on a 6809. This demo drops three coins into it and goes looking
for the credits, and the search does not end on one byte: three of them hold 3. Change watches on
two of them tell the story the scan cannot: the coin routine increments one (`INC $042B`) and
then adds one in BCD to the other (`ADDA $042C`, `DAA`, `STA $042C`), so the game keeps its
credits twice, in binary and in BCD. A START is stopped by each watch in turn, at the binary
decrement and then at the BCD store, and the history behind that stop is the routine that took
the credit. A saved state takes the START back, and the picture is the game in play.

## The ROM

The set is one of the ROMs [mamedev.org](https://www.mamedev.org/roms/) distributes for free,
non-commercial use, from its own site only, so it is not in this repository. Get it and check it
with your MAME:

```sh
mkdir -p ~/roms && curl -fL -o ~/roms/gridlee.zip https://www.mamedev.org/roms/gridlee/gridlee.zip
mame -rompath ~/roms -verifyroms gridlee
```

## Run it

```sh
uv run python demos/gridlee/demo.py --rompath ~/roms
```

- `--binary PATH` picks the MAME to start; left out, `MAME_BINARY`, else the `mame` on your
  `PATH`.
- `--display N` opens the window on that display; left out, on the host's main one. The
  window opens behind, so the run takes nobody's focus.
- `--transcript PATH` moves the whole transcript; the run's other files go beside it.
- `--update-readme` rewrites the block below, `TRANSCRIPT.md`, `screen.png` and `loop.mp4` from a run where every step
  passed.

Each line it prints is one call and its check. Exit codes: 0 every step passed, 1 a step
failed, 2 a usage error, 3 nothing was demonstrated (a missing ROM, a relative path, a server
that did not start).

## The prompt

Give this to an MCP client with this server connected:

> Start `gridlee` with the ROMs in `~/roms` (as an absolute path), checking it against its first
> program ROM, CRC 1C43539E, unzipped from `gridlee.zip` and given as the reference image at
> `0xa000`. Let the attract mode run for five seconds. Open a value scan over `0x0`, 2 KB, and
> after each of three coins (`:IN1`, `Coin 1`, held four frames) and two seconds of running,
> keep only the bytes that equal the number of coins so far. Put a watch that stops on a change of
> `0x42b` and another on `0x42c`, drop a fourth coin, and run half a second at a time until both
> have stopped the machine and a third half second runs clean: tell me which instruction writes
> each, and disassemble 12 bytes from `0xb583`. Read both bytes and save a state. Press
> `1 Player Start` and tell me which instruction each watch names as the START takes the credit,
> running one frame on after the first stop; show me the last eight instructions the cpu ran and
> the registers. Clear both watches, let the game play for eight seconds, read both bytes, take a
> picture of the screen, load the state back, read them again and close the session.

## What it walks

| Family | Calls |
|---|---|
| Session | `start` (checked against the ROM), `close` |
| Advance | `run_for` by emulated milliseconds and by frames, with its frame and cycle survey |
| Scan | `scan(method="start")` and `scan(method="filter")` |
| Declarations | `watch_add` (through `perform`), each watch's stop naming its writer, `declaration_clear(kind="watch")` |
| Read | `read_memory`, `disassemble` (the coin routine), the START's trail in `history`, `registers` |
| Lua | `input` (the coin slot and the START button; the watches stop the START while it is still held) |
| Lists | `perform` (coin, run, filter in one call; both watches in one) |
| States | `state_write(method="save")`, `state_write(method="load")` (verified) |
| Screen | `screen_view` |
